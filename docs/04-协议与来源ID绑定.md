# 04 · 协议 `ai-status/1` 与来源 ID 绑定

协议版本 `ai-status/1` v1.0.0 自 2026-11-06 保持不变；v1.5.0 固件只**新增可选字段 `src`**，旧字段语义一字未改。

## 一、状态枚举

`state` 为小写下划线 ASCII 字符串，PC 端不要传中文。未知状态返回 `invalid_state` 并被忽略。

| state | 中文 | 优先级 | 粘性 | 默认 TTL | 触发时机 |
| --- | --- | ---: | --- | ---: | --- |
| `offline` | PC 未连接 / 心跳超时 | 0 | 否 | 永久 | 设备侧自动判定，PC 不主动发 |
| `idle` | 空闲待命 | 10 | 否 | 心跳续期 | 会话存在但无任务 |
| `thinking` | 思考中 | 20 | 否 | 心跳续期 | 收到需求、规划中 |
| `searching` | 找资料 | 25 | 否 | 心跳续期 | 搜索网页、读文档 |
| `coding` | 脚本编写中 | 30 | 否 | 心跳续期 | 写代码、改文件、执行命令 |
| `outputting` | 输出中 | 30 | 否 | 心跳续期 | 正在向用户输出回答 |
| `done` | 完成 | 40 | 否 | **10000ms** | 任务结束，TTL 到后回 `idle` |
| `need_input` | 需求要回复信息 | 80 | **是** | 永久 | 等待用户补充信息 |
| `need_confirm` | 需要确定 | 85 | **是** | 永久 | 等待确认方案 / 授权 |
| `error` | 异常 / 失败 | 90 | **是** | 永久 | 工具报错、任务失败、处理时间过长 |

预留 `reading` / `tool_use` / `paused`，协议版本号不变，未知 state 不会让设备崩溃。

> PC 端 v1.3.1 起：`need_confirm` / `need_input` 只由明确的确认 / 提问信号触发，不再用静默窗口猜；工具真实失败（IDE 返回 `Error calling tool: ...`）会立即上报 `error` 红色快闪，3 秒后自动消退回工作态。固件 v1.5.0-fx 的 `done` 默认 TTL 已是 10000ms，PC 帧同样带 `ttl=10000`，两侧一致。详见 `docs/02` 第七节。

## 二、灯光表现（单颗 WS2812，RGB 可配置）

v1.5.0-fx 起每个状态的颜色 / 效果 / 亮度 / 周期都可在网页或 `POST /api/fx` 里改，存 NVS。下表是**内置默认值**：

| state | 中文 | 主色 RGB | 辅色 RGB | 动效 | 亮度 | 周期 |
| --- | --- | --- | --- | --- | --- | --- |
| `offline` | 离线 | `5,10,20` | — | 常亮 | 18% | — |
| `idle` | 空闲 | `10,30,90` | — | 常亮 | 30% | — |
| `thinking` | 思考 | `42,8,70` | `90,24,144` | 渐变呼吸 | 38% | 3000ms |
| `searching` | 找资料 | `10,90,42` | `122,106,10` | 渐变呼吸 | 38% | 1800ms |
| `coding` | 编写 | `10,110,140` | — | 呼吸 | 40% | 1200ms |
| `outputting` | 输出 | `10,58,106` | `16,160,160` | 渐变流动 | 40% | 3000ms |
| `done` | 完成 | `26,160,58` | — | 闪烁（慢闪） | 55% | 1000ms，TTL 10s 后回 `idle` |
| `need_input` | 需补充 | `255,79,168` | — | 闪烁（快闪） | 95% | 500ms |
| `need_confirm` | 需确认 | `255,138,26` | — | 闪烁（快闪） | 100% | 500ms |
| `error` | 失败 | `255,32,32` | — | 闪烁（急闪） | 100% | 240ms |

设计意图：工作态偏暗（18%~40%）不刺眼，交互态明显更亮（95%~100%）一眼能看到。`STATUS_FX_DEFAULT` → NVS `fx_v1` → 运行时可改，`{"reset":1}` 恢复默认。

## 三、通用状态字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `state` | string | 是 | 枚举值 |
| `seq` | uint32 | 建议 | 单调递增；`0` 表示不检查顺序。v1.5 起按来源独立 |
| `ttl` / `ttl_ms` | int | 否 | 状态有效时长(ms)，缺省用默认值 |
| `msg` | string | 否 | ≤120 字符，仅用于 WS 推送与日志，不参与灯光 |
| `force` | 0/1 | 否 | 为 1 时忽略优先级检查 |
| `reqId` | string | 否 | 原样回显，便于异步关联 |
| **`src`** | string | 否 | **v1.5 新增**：来源 ID，≤40 字节 |

### 三通道示例

串口 JSON Lines（PC 优先通道，115200 8N1，一行一帧 ≤512B）：

```json
{"t":"status","v":1,"src":"PC-A","state":"thinking","seq":42,"ttl":15000,"msg":"[PC-A] 正在分析需求"}
{"t":"heartbeat","v":1,"src":"PC-A","state":"thinking","seq":43}
```

HTTP（必须带 `Content-Type: application/json`）：

```json
POST /api/status
{"state":"need_confirm","seq":43,"src":"PC-A","msg":"[PC-A] 是否覆盖文件?","force":0,"reqId":"r9"}
→ {"ok":true,"state":"need_confirm","seq":43,"prio":85,"reqId":"r9"}
```

WebSocket：

```json
{"cmd":"status_set","val":{"state":"thinking","seq":42,"src":"PC-A","ttl":15000,"msg":"..."},"reqId":"r1"}
{"type":"status","data":{"state":"thinking","seq":42,"prio":20,"sticky":false,"since_ms":1234,"link":true,"msg":"...","src":"PC-A","bindMode":0}}
```

## 四、来源 ID（`src`）约定

| 项 | 约定 |
| --- | --- |
| 字段名 | `src`（PC 端 `SOURCE_FIELD`，可用 `source_field` 配置） |
| 生成 | PC 首次运行生成「主机名 + 随机后缀」，存 `client_id.json`，重启不变 |
| 长度 | ≤40 字节；逗号与控制字符被规范为 `_` |
| 缺省 | 不带 `src` 的旧客户端 / 网页手动操作统一视为匿名来源 `*` |
| `msg` 标签 | PC 端自动加 `[来源ID]` 前缀。设备会把 `msg` 原样放进 WS 广播与 `/api/status`，**所以不改固件也能追溯** |
| 多窗口 | 同一台 PC 想区分窗口，可用 `PC-A#win1` 之类的不同 `src`，设备会各自建槽 |
| 每来源独立 | 状态、`seq`、优先级、TTL、粘性、15s 超时按 `src` 单独计时，互不覆盖 |
| 槽位上限 | 8 个来源，满时淘汰最久未更新者 |

> 换电脑时**不要复制 `client_id.json`**，否则两台电脑 ID 相同、白名单无法区分。

## 五、绑定机制（v1.5.0）

| 模式 | 含义 |
| --- | --- |
| `bindMode = 0` | 全部接受（默认，完全兼容 v1.4.x），所有来源参与聚合 |
| `bindMode = 1` | 仅绑定来源：只有白名单里的 `src` 参与灯效聚合 |

- 白名单最多 8 条，可逐条增删/一键清空，存 NVS `status_cfg/bind_srcs` + `status_cfg/bind_mode`，开机恢复、立即生效。
- 未绑定来源**仍被记录和显示**（方便事后勾选），但不参与聚合；其状态帧回 `ok=false / reason=source_not_bound`。
- 单灯聚合：取所有「已绑定且在线」来源中优先级最高的状态；同级取最近变化者。
- 网页「来源与绑定」卡片可查看每个来源的状态、`msg`、心跳距今、在线/离线并勾选。

设置接口：

```json
WS    {"cmd":"status_bind","val":{"src":"PC-A","on":1}}
WS    {"cmd":"bind_mode","val":1}          /  {"cmd":"bind_clear","val":1}
HTTP  POST /api/bind  {"src":"PC-A","on":1,"mode":1,"clear":0}
串口  {"t":"bind","v":1,"src":"PC-A","on":1}   /  {"t":"bind_mode","v":1,"val":1}
查询  GET /api/sources 、 GET /api/bind 、 WS {"cmd":"sources_get","val":1} 、 串口 {"t":"sources"}
```

## 六、准入规则、心跳与超时

准入顺序：

```
1. JSON 解析失败 / 超长      → invalid_json / payload_too_large
2. state 不在枚举内           → invalid_state
3. seq != 0 且 seq <= 本来源 lastSeq → invalid_seq
4. 状态引擎未启用             → disabled
5. prio(new) < prio(current) 且 force != 1 → lower_priority
6. （v1.5）mode=1 且 src 未绑定 → source_not_bound
7. 通过 → 更新状态、刷新 lastFrameMs、广播 status / sources
```

例外：`done` TTL 回落 `idle`、心跳超时回落 `offline` 属于设备内部转移，不走优先级检查。设备内部转移也会自增 seq，所以 PC 端必须处理 `invalid_seq`（本项目会自动重同步并补发一次）。

| 参数 | 值 |
| --- | --- |
| 心跳间隔 | 5000ms（PC 必须实现） |
| 心跳超时转 `offline` | 15000ms，粘性状态除外（只是 `link=false`，灯继续闪） |
| `done` TTL | 10000ms（固件 v1.5.0-fx 默认即 10000ms，PC 帧同样带 `ttl=10000`） |
| 重连退避 | 1→2→4→8 秒，成功后重发当前状态 |
| 最短状态驻留 | PC 端 300ms，避免灯色乱跳 |

## 七、设备发现流程（PC 端必须实现）

```
① 串口直连（最高优先）
   枚举 VID_303A:1001（原生 USB CDC）/ VID_1A86:55D3（CH343）
   → 115200 8N1，DTR/RTS = false
   → {"t":"ping","v":1}\n，等 ≤800ms
   → pong.proto == "ai-status/1" 即命中
② 局域网回落
   cached_ip → mDNS esp32s3-ai.local → ARP 按 MAC 前缀反查
   → 并发扫 /24 的 GET /api/hello → AP 兜底 192.168.4.1
   → hello.proto == "ai-status/1" 即命中
③ 都失败
   提示连接 AP，保持指数退避重试
④ 运行时
   5s 心跳；断线重连后先读当前 seq，再补发状态
```

跨网段时广播/mDNS/扫描都无效，只剩 USB 串口直连；串口 `pong` 会带回设备当前 IP。

## 八、错误码速查

见 `docs/03-ESP32端固件与接口.md` 第八节。最常遇到的三个：`invalid_seq`（自动重同步）、`lower_priority`（不要重试）、`source_not_bound`（去网页勾选来源）。

## 九、兼容性与安全边界

- v1.4.x 全部接口、命令、字段语义不变；新增字段一律并列添加。
- 不带 `src` / `seq` / `reqId` 的旧客户端行为与旧版完全一致。
- 设备只维护「一个当前态」（v1.5 起按来源各一份），无历史记录，统计需 PC 端落库。
- 无鉴权、无 TLS、`/api/*` 开放 CORS；同网段任何设备都能改灯 / 改 WiFi / 重启。**仅可信局域网使用**。
- 串口协议行被设备截获，不会出现在网页终端；调试时看 `usb_info` 的 RX/TX 计数。
