# 02 · PC 端功能与配置（v1.2.0）

## 一、架构与数据流

```
CodeBuddy Hooks（每个事件启动一个短命进程）
        │  stdin: Hook JSON
        ▼
main.py hook ──HTTP POST──► 127.0.0.1:8765/event
                                  │
                    ┌─────────────▼─────────────┐
                    │  StatusService（常驻）      │
                    │  · 事件总线 /health /state  │
                    │  · StateMachine 多会话仲裁  │
                    │  · 5s 心跳 / 断线重连       │
                    └─────────────┬─────────────┘
                                  │ src + msg[来源ID]
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
   串口 JSON Lines（优先）                  HTTP POST /api/status
   COM16 原生 USB CDC / COM17 CH343        mDNS / ARP / /24 扫描 / AP
```

**为什么必须有常驻服务**：Hooks 每次事件都启动新进程，无法持有串口长连接，也无法维持 5s 心跳；因此 Hook 端只做一次极轻的本地 HTTP 调用（失败静默、永不阻断 AI），其余全部交给服务。

模块职责：

| 文件 | 职责 |
| --- | --- |
| `main.py` | CLI 入口、配置加载、来源 ID 生成、Hooks 配置生成/安装、自检 |
| `ai_status/protocol.py` | 状态枚举、优先级、TTL、串口/HTTP 帧构造、`src` 与 `msg` 标签 |
| `ai_status/mapper.py` | Hooks 事件 → 状态（兼容 IDE 与 CLI 两套工具名） |
| `ai_status/state.py` | 多会话仲裁、粘性状态、最短驻留、`done`/`idle` 回落 |
| `ai_status/serial_win.py` | Windows 零依赖串口（Win32 ctypes；pyserial 可选优先） |
| `ai_status/device.py` | 设备发现、seq 同步、心跳、重连、回执处理 |
| `ai_status/service.py` | 本地 HTTP 事件总线与主调度循环 |

## 二、状态映射

| Hooks 事件 / 观察点 | 上报状态 |
| --- | --- |
| `SessionStart`、`SessionEnd` | `idle` |
| `UserPromptSubmit`（收到新需求） | `thinking` |
| `PreToolUse`：`web_search` / `web_fetch` / `read_file` / `search_content` / `list_dir` / `Grep` / `Glob` / `Task` 等 | `searching` |
| `PreToolUse`：`write_to_file` / `replace_in_file` / `execute_command` / `Write` / `Edit` / `Bash` 等 | `coding` |
| `PreToolUse`：审批字段命中（`requires_approval` / `requiresApproval` / `autoApprove:false` / `permission:"ask"` 等） | `need_confirm`（直接上报） |
| `PreToolUse`：`ask_followup_question` 等提问工具，或 `tool_input.questions` 非空 | `need_input`（直接上报） |
| **`PreToolUse` 后 4s 仍无 `PostToolUse`** | **`need_confirm`（静默推断，`force=1`）** |
| **`PostToolUse` / `Stop` 后静默 2.5s** | **`need_input`（静默推断，`force=1`）** |
| `PostToolUse` 成功 | 解除已有等待态，回到 `thinking` |
| `PostToolUse` 返回失败 / `PostToolUseFailure` / `PermissionDenied` | `error`（等待态期间会被锁定挡住） |
| `Notification`：`permission_prompt` / `PermissionRequest` | `need_confirm` |
| `Notification`：`idle_prompt` / `elicitation_dialog` / `Elicitation` | `need_input` |
| `Stop`（一轮回复完成） | `done` |
| 工具结束后 1.2s 无活动（启发式，可关） | `outputting` |
| Hook 载荷里带 `ai_status_state` | 显式覆盖为指定状态（带 `force` 可突破锁定） |

工具名同时兼容 IDE 风格（`write_to_file`）与 CLI 风格（`Write`）。完整清单见 `ai_status/mapper.py`。

> **为什么需要推断**：IDE 版实际只稳定发出 7 个事件，确认框、提问框**不会产生任何 Hooks 事件**，且 `tool_name` 经常为空；实测事件流里连 `Stop` 都可能整段缺失。因此 `need_confirm` / `need_input` 不能只靠事件名映射，必须结合「静默窗口」判断。详见第七节。

| --- | --- |

## 四、本地 HTTP 端点（仅监听 127.0.0.1）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/event`、`/hook` | 接收 Hook 事件 JSON |
| POST | `/state` | `{"state":"...","msg":"...","force":true}` 手工设置 |
| POST | `/clear` | 解除粘性状态并释放 LED |
| GET | `/health` | 当前状态、`sticky` / `waiting_for_human` / `watch`、各会话状态、设备链路、seq、事件数、`source_id`、最后一帧 |
| GET | `/identity` | 本机来源 ID 与字段名 |

## 六、Hooks 事件与安装

IDE 版实际稳定发出**前 7 个**；后 5 个是 v1.2.0 起默认注册的补强事件——IDE 不发时完全无副作用，一旦发出即可精确命中确认/提问状态：

| 事件 | matcher |
| --- | --- |
| `SessionStart` | `startup` |
| `UserPromptSubmit` | — |
| `PreToolUse` | `.*` |
| `PostToolUse` | `.*` |
| `Stop` | — |
| `SessionEnd` | `other` |
| `PreCompact` | `""` |
| `Notification` | `""` |
| `PermissionRequest` | `""` |
| `PermissionDenied` | `""` |
| `PostToolUseFailure` | `.*` |
| `Elicitation` | `""` |

CLI 增量事件（`--with-cli`）：`StopFailure`、`SubagentStop`、`ElicitationResult`（与上表重叠的事件合并时按命令去重）。

> 从 v1.1.0 升级后**建议重跑一次** `python main.py install-hooks --write --scope user`，把新增事件补进 `settings.json`。不重跑也不影响静默推断，只是少了「精确命中」这条通道。

生成的每条命令形如：

```json
"command": "\"<Python解释器>\" \"<APP>/main.py\" hook --event PreToolUse --port 8765"
```

每个事件带不同的 `--event` 参数，既避免 Hooks 的相同命令去重，也能在 stdin 缺字段时补全事件名。Hook 客户端 0.4 秒超时、失败静默、永远返回 `{"continue":true,"suppressOutput":true}` 并退出 0，**不会阻断 AI**。

## 七、状态机行为

- **多会话仲裁**：按 `session_id` 记录各窗口状态，取 `(优先级, 更新时间)` 最高者。多个窗口默认混合显示一个状态（当前版本不区分窗口）。
- **粘性状态**：`need_confirm` / `need_input` / `error` 是全局粘性的，任何窗口触发都会压住其它状态，直到用户响应、`SessionEnd` 或 `clear`。其中前两者额外受「人工介入锁定」保护，见 7.2。
- **最短驻留**：低/同级状态 300ms 内不重复切换，避免灯闪烁失去辨识度；粘性状态不受此限制。
- **自动回落**：`done` 5 秒回 `idle`；长时间无事件回 `idle`；停心跳 15 秒设备自行 `offline`。**等待态不回落**，这是刻意的。
- **seq**：单调递增；设备内部转移会自增 seq，PC 收到 `invalid_seq` 会自动重同步并补发一次。
- **重连**：断连后按 1→2→4→8 秒指数退避，成功后重新同步 seq 并补发当前状态。
- **回执处理**：`lower_priority` 不重试；`disabled` 提示打开状态引擎；`source_not_bound` 提示去设备网页勾选本机来源。

### 7.1 「需要人处理」怎么推断（v1.2.0 核心）

IDE 版确认框 / 提问框不发任何事件、`tool_name` 常为空、实测连 `Stop` 都可能整段缺失，所以用三层信号，优先级从高到低：

| 层 | 信号 | 结果 |
| --- | --- | --- |
| ① 显式 | Hook 载荷带 `ai_status_state`，或 `POST /state` 手工上报 | 直接切到指定状态；带 `force` 可突破锁定 |
| ② 事件 | `Notification(permission_prompt)` / `PermissionRequest` / `Elicitation`；`PreToolUse` 的审批字段或提问工具 | 立即 `need_confirm` / `need_input`，不等超时 |
| ③ 推断 | `PreToolUse` 后 4s 仍无 `PostToolUse` | `need_confirm`（工具卡在授权弹窗） |
| ③ 推断 | `PostToolUse` / `Stop` 后静默 2.5s | `need_input`（本轮收尾，等用户回复） |

状态机内部用 `_watch = (confirm|input, 起始时间, session)` 记录观察窗口，服务每 0.1s `tick()` 一次。任何新事件都会取消或重建观察窗口，所以工具正常完成不会误报。**`PostToolUse` 是关键观察点**，因为它不依赖 IDE 是否发 `Stop`。

默认灯效节奏：工具结束 → 1.2s `outputting`（渐变流动）→ 2.5s `need_input`（粉白双闪并保持）。

### 7.2 最高优先级与不可覆盖

- `need_input`(80) / `need_confirm`(85) 建立后写入全局 `sticky`，并以 `force=1` 推给设备，确保设备端即使停在 `error`(90) 也能切过去。
- 锁定期间 `coding` / `searching` / `done` / `error` / 工具失败 / `Stop` **一律被忽略**，PC 端不推任何状态帧；心跳仍带当前等待态，灯不会被改掉。
- **只允许升级不允许降级**：`need_input` → `need_confirm` 可以，反向不行。
- 工具报错不等于「用户已处理等待」，因此 `error` 不再抢占等待态。

### 7.3 什么时候才解除

| 解除信号 | 含义 |
| --- | --- |
| `UserPromptSubmit` | 用户回复 / 发了新需求 |
| `PostToolUse` | 用户点了确认（或工具本来就在跑），流程继续 |
| `need_input` 期间来了新的 `PreToolUse` | 用户已回复、AI 重新开始调用工具 |
| `SessionStart` / `SessionEnd` | 会话切换 / 结束 |
| `python main.py clear` / `POST /clear` | 手动解除 |
| `POST /state` 带 `force:true`、`emit --force`、Hook 载荷带 `release_sticky:true` | 显式强制解除 |

解除时以 `force=1` 把设备端从 80/85/90 拉回 `thinking`(20)，并清空所有会话里残留的等待态，避免多窗口下 `sticky` 已清、`current` 却仍被别的会话等待态顶回来的失配。

### 7.4 调参与排错

| 现象 | 处理 |
| --- | --- |
| 执行很久的命令（编译、安装）被误判成等待确认 | 把 `need_confirm_after_ms` 调到 `8000`~`15000`；工具恢复执行后会自动解除 |
| 不想让「等回复」一直常亮 | 设 `infer_need_input:false`（恢复 `done` 5s 回 `idle`），或调大 `need_input_after_ms` |
| 想完全回到 v1.1.0 行为 | `infer_need_confirm:false` + `infer_need_input:false`，只保留显式/事件通道 |
| 判断是谁触发了推断 | `GET /health` 看 `state.waiting_for_human` / `state.watch` / `state.sticky`；`GET /events` 看每条的 `watch` / `release_sticky` |
| 灯一直不解除 | IDE 既没发 `UserPromptSubmit` 也没发 `PostToolUse`；用 `python main.py clear` 手动释放 |

## 八、设备发现顺序

1. 串口：枚举 `VID_303A:1001` / `VID_1A86:55D3` → `ping` 等 `pong` 且 `proto == ai-status/1`
2. 局域网：`cached_ip` → mDNS `esp32s3-ai.local` → ARP 按 MAC 前缀反查 → 并发扫 /24 的 `/api/hello` → AP 兜底 `192.168.4.1`
3. 都找不到：日志提示连接设备 AP；服务仍继续运行并定时重试

## 九、来源 ID（`src`）

- 每台电脑首次运行生成稳定 ID（主机名 + 随机后缀），写入 `client_id.json`。
- 所有状态帧、心跳、`clear`、`get`、`ping` 都带 `src`；`msg` 额外带 `[ID]` 前缀。
- 设备 v1.5.0 按 `src` 为每个来源独立维护状态，并在网页「来源与绑定」显示列表；可勾选只接受某几台。
- 查 ID：`python main.py identity`、`GET /identity`、`GET /health`。

## 十、日志与健康检查

- 控制台与 `ai_status.log` 同时输出，格式 `时间 [级别] 状态 -> xxx 原因 reply=...`。
- `GET /health` 是最有用的排错入口：`event_count` 为 0 说明 Hooks 没生效；`device.kind` 显示当前通道；`device.last_frame` 显示最后一帧（含 `src` 与 `msg`）；`state.waiting_for_human` / `state.watch` 显示等待态与当前观察窗口。
- 服务不会把任何数据发到公网：事件总线只监听本机，设备接口仅可信局域网。
