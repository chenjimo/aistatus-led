# 02 · PC 端功能与配置（v1.3.0）

## 一、架构与数据流

```
CodeBuddy Hooks（每个事件启动一个短命进程）
        │  stdin: Hook JSON
        ▼
main.py hook ──HTTP POST──► 127.0.0.1:8765/event
                                  │
                    ┌─────────────▼─────────────┐
                    │  StatusService（常驻）      │
                    │  · 事件总线 /health /state  │
                    │  · StateMachine 多会话仲裁  │
                    │  · 5s 心跳 / 断线重连       │
                    └─────────────┬─────────────┘
                                  │ src + msg[来源ID]
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
   串口 JSON Lines（优先）                  HTTP POST /api/status
   COM16 原生 USB CDC / COM17 CH343        mDNS / ARP / /24 扫描 / AP
```

**为什么必须有常驻服务**：Hooks 每次事件都启动新进程，无法持有串口长连接，也无法维持 5s 心跳；因此 Hook 端只做一次极轻的本地 HTTP 调用（失败静默、永不阻断 AI），其余全部交给服务。

模块职责：

| 文件 | 职责 |
| --- | --- |
| `main.py` | CLI 入口、配置加载、来源 ID 生成、Hooks 配置生成/安装、自检 |
| `ai_status/protocol.py` | 状态枚举、优先级、TTL、串口/HTTP 帧构造、`src` 与 `msg` 标签 |
| `ai_status/mapper.py` | Hooks 事件 → 状态（兼容 IDE 与 CLI 两套工具名） |
| `ai_status/state.py` | 多会话仲裁、粘性状态、最短驻留、`done`/`idle` 回落 |
| `ai_status/serial_win.py` | Windows 零依赖串口（Win32 ctypes；pyserial 可选优先） |
| `ai_status/device.py` | 设备发现、seq 同步、心跳、重连、回执处理 |
| `ai_status/service.py` | 本地 HTTP 事件总线与主调度循环 |

## 二、状态映射

| Hooks 事件 / 信号 | 上报状态 | 灯效 |
| --- | --- | --- |
| `SessionStart`、`SessionEnd`，或长时间无事件 | `idle` | 暗色深蓝常亮 |
| `UserPromptSubmit`（收到新需求） | `thinking` | 紫色呼吸 |
| `PreToolUse`：`web_search` / `read_file` / `search_content` / `Grep` / `Glob` / `Task` 等 | `searching` | 黄色慢闪 |
| `PreToolUse`：`tool_name` 为空或未知 | `thinking` | 紫色呼吸 |
| `PreToolUse`：`write_to_file` / `execute_command` / `Write` / `Edit` / `Bash` 等 | `coding` | 浅蓝青呼吸 |
| `PostToolUse` 成功 | `thinking`（并解除等待态） | 紫色呼吸 |
| `Stop`（一轮回复完成） | `done`，10s 后 `idle` | 绿色常亮（`ttl=10000`） |
| Hook 载荷带 `ai_status_state: "outputting"` | `outputting` | 渐变流动 |
| 审批字段命中（`requires_approval` / `autoApprove:false` / `permission:"ask"` 等）、`PermissionRequest`、`Notification(permission_prompt)` | `need_confirm` | 橙色快闪 |
| 提问工具 / `questions` 字段、`Elicitation`、`Notification(idle_prompt)` | `need_input` | 粉白双闪 |
| `PostToolUse` 的 `tool_response` 以 `Error calling tool:` 开头（IDE 实测格式）、`PostToolUseFailure`、`PermissionDenied`、`StopFailure` | `error` | 红色快闪，3s 后自动消退 |
| 工作中卡住超过 `stalled_after_ms`（默认关闭，可选兜底） | `error` | 红色快闪 |
| Hook 载荷里带其它 `ai_status_state` | 显式覆盖为指定状态（带 `force` 可突破锁定） | 对应灯效 |

工具名同时兼容 IDE 风格（`write_to_file`）与 CLI 风格（`Write`）。完整清单见 `ai_status/mapper.py`。

> **v1.3.0 原则：零猜测**。实测 IDE 版 `PreToolUse` 数量远大于 `PostToolUse`（工具完成事件经常根本不发），v1.2.0 曾据此用「静默窗口」推断等待态，结果把深度思考误报成 `need_input` / `need_confirm`。该推断已**整体移除**：静默永远不会被当成「需要人处理」，深度思考稳定显示 `thinking`（紫色呼吸）。只有真实的确认 / 提问 / 失败事件才点亮快闪；真正卡住超过 3 分钟则归为红色 `error`。详见第七节。

## 六、Hooks 事件与安装

IDE 版实际稳定发出**前 7 个**；后 5 个是 v1.2.0 起默认注册的补强事件——IDE 不发时完全无副作用，一旦发出即可精确命中确认/提问状态。v1.3.0 起，这些事件是 `need_confirm` / `need_input` 的**唯一自动触发途径**：

| 事件 | matcher |
| --- | --- |
| `SessionStart` | `startup` |
| `UserPromptSubmit` | — |
| `PreToolUse` | `.*` |
| `PostToolUse` | `.*` |
| `Stop` | — |
| `SessionEnd` | `other` |
| `PreCompact` | `""` |
| `Notification` | `""` |
| `PermissionRequest` | `""` |
| `PermissionDenied` | `""` |
| `PostToolUseFailure` | `.*` |
| `Elicitation` | `""` |

CLI 增量事件（`--with-cli`）：`StopFailure`、`SubagentStop`、`ElicitationResult`（与上表重叠的事件合并时按命令去重）。

> 从 v1.1.0 升级后**建议重跑一次** `python main.py install-hooks --write --scope user`，把新增事件补进 `settings.json`。v1.3.0 起 IDE 不发这些事件时，`need_confirm` / `need_input` 就不会自动亮——这是刻意的：宁可不亮，也不乱亮。

生成的每条命令形如：

```json
"command": "\"<Python解释器>\" \"<APP>/main.py\" hook --event PreToolUse --port 8765"
```

每个事件带不同的 `--event` 参数，既避免 Hooks 的相同命令去重，也能在 stdin 缺字段时补全事件名。Hook 客户端 0.4 秒超时、失败静默、永远返回 `{"continue":true,"suppressOutput":true}` 并退出 0，**不会阻断 AI**。

## 七、状态机行为

- **多会话仲裁**：按 `session_id` 记录各窗口状态，取 `(优先级, 更新时间)` 最高者。多个窗口默认混合显示一个状态（当前版本不区分窗口）。
- **粘性状态**：`need_confirm` / `need_input` / `error` 是全局粘性的，任何窗口触发都会压住其它状态，直到用户响应、`SessionEnd` 或 `clear`。其中前两者额外受「人工介入锁定」保护，见 7.4。
- **最短驻留**：低/同级状态 300ms 内不重复切换，避免灯闪烁失去辨识度；粘性状态不受此限制。
- **自动回落**：`done` **10 秒**回 `idle`（PC 端 `force=1` + 帧 `ttl=10000`，固件侧同步回落）；非工作态长时间无事件回 `idle`；停心跳 15 秒设备自行 `offline`。**等待态不回落**，这是刻意的。
- **seq**：单调递增；设备内部转移会自增 seq，PC 收到 `invalid_seq` 会自动重同步并补发一次。
- **重连**：断连后按 1→2→4→8 秒指数退避，成功后重新同步 seq 并补发当前状态。
- **回执处理**：`lower_priority` 不重试；`disabled` 提示打开状态引擎；`source_not_bound` 提示去设备网页勾选本机来源。

### 7.1 状态分类（v1.3.0）

| 大类 | 状态 | 灯效 | 由什么驱动 |
| --- | --- | --- | --- |
| 空闲 | `idle` | 暗色深蓝常亮 | `SessionStart` / `SessionEnd` / `done` 到期 / 长时间无事件 |
| 工作中 | `thinking` | 紫色呼吸 | `UserPromptSubmit`、`PostToolUse`、工具名为空或未知 |
| 工作中 | `searching` | 黄色慢闪 | 检索 / 读文件类 `PreToolUse` |
| 工作中 | `coding` | 浅蓝青呼吸 | 写文件 / 执行命令类 `PreToolUse` |
| 工作中 | `outputting` | 渐变流动 | 显式 `ai_status_state`（默认不做静默推断） |
| 完成 | `done` | 绿色常亮 10s | `Stop` |
| 需要我处理 | `need_input` | 粉白双闪 | 提问工具 / `questions` / `Elicitation` / `Notification(idle_prompt)` |
| 需要我处理 | `need_confirm` | 橙色快闪 | 审批字段 / `PermissionRequest` / `Notification(permission_prompt)` |
| 需要我处理 | `error` | 红色快闪 | 工具失败类事件，或工作中卡住超过 `stalled_after_ms` |

> 颜色与动效由固件 `STATUS_DEFS` 定义，PC 端只决定「上报哪个状态」和 `ttl`。所以本次改动**没有动固件**：10 秒时长由 PC 帧的 `ttl` 覆盖实现；而「黄色呼吸」「绿色慢闪」这类动效差异属于固件侧，仅改 PC 端做不到。

### 7.2 为什么不再推断「等待人」

v1.2.0 假设「`PreToolUse` 后迟迟没有 `PostToolUse` = 卡在授权弹窗」「工具结束静默 = 等用户回复」。真实事件流证伪了这个假设：

| 实测 | 数值 |
| --- | --- |
| 某次 39 条事件中 `PreToolUse` / `PostToolUse` | 29 / 9（完成事件大量缺失） |
| 另一批 50 条事件里 `PostToolUse → PreToolUse` 静默窗口 | 5~60 秒，共 20+ 个 |
| v1.2.0 在这 50 条上打出的等待态帧 | **23 帧**（22 `need_input` + 1 `need_confirm`），几乎全是深度思考误报 |
| v1.3.0 同样 50 条 | **0 帧误报**，只有 `searching` 14 / `coding` 7 / `thinking` 17 |

结论：**Hooks 事件流无法区分「AI 在深度思考」和「AI 在等人」**。v1.3.0 彻底放弃这种猜测：静默时保持 `thinking`（紫色呼吸），只有明确的确认 / 提问 / 失败信号才点亮快闪。

代价也说清楚：IDE 版实测不发 `PermissionRequest` / `Elicitation`，也不带审批字段，所以 `need_input` / `need_confirm` 在 IDE 下基本不会自动亮。这是「不误报」的必然取舍；一旦 IDE 补发这些事件或字段，PC 端无需升级即可命中，也可用 `ai_status_state` / `POST /state` 显式上报。

### 7.3 失败如何识别、红闪如何消退

**只认真实失败信号**，不做时间猜测：

| 信号 | 判定 |
| --- | --- |
| `PostToolUse.tool_response` 是字符串且以 `Error calling tool:` 开头（IDE 实测格式，如 `Error calling tool: Could not find file 'x'.`） | `error` |
| `tool_response` 是 dict：`success:false` / `is_error:true` / `exitCode≠0` / `error` 非空 | `error` |
| `PostToolUseFailure` / `PermissionDenied` / `StopFailure` | `error` |

只认**前缀**：文件内容里出现 `error` 字样不会被误判（自检有专门用例 `内容含 error 字样不误报`）。

红闪节奏：立即 `force=1` 推 `error` → 保持 `error_hold_ms`（默认 3s）→ 期间没有新事件就自动消退回工作态；AI 已经继续干活（新的 `PreToolUse` / `PostToolUse`）则立即解除。

`stalled_after_ms` 默认 `0`（关闭）：它只能靠「多久没事件」猜卡住，而 IDE 对 `execute_command` 根本不发 Hooks，长命令必然被误判成红闪；需要兜底时设 `300000`。

### 7.4 最高优先级与「处理完就消」

- `need_input`(80) / `need_confirm`(85) 建立后写入全局 `sticky`，并以 `force=1` 推给设备，确保设备端即使停在 `error`(90) 也能切过去。
- 等待期间**无关事件**（`PreCompact` 等纯通知）被忽略，灯不会被乱改。
- **AI 重新开始工作（任意 `PreToolUse`）或本轮结束（`Stop`）会立即解除等待态**——IDE 实测 `UserPromptSubmit` 经常不发，`PreToolUse` 才是「已放行」最可靠的信号。这是「处理完就消」的关键。
- 只允许升级不允许降级：`need_input` → `need_confirm` 可以，反向不行。

### 7.5 什么时候才解除

| 解除信号 | 含义 |
| --- | --- |
| `UserPromptSubmit` | 用户回复 / 发了新需求 |
| `PostToolUse` | 用户点了确认（或工具本来就在跑），流程继续 |
| `need_input` 期间 AI 又开始工作（`PreToolUse` 等） | 用户已回复 |
| `SessionStart` / `SessionEnd` | 会话切换 / 结束 |
| `python main.py clear` / `POST /clear` | 手动解除 |
| `POST /state` 带 `force:true`、`emit --force`、Hook 载荷带 `release_sticky:true` | 显式强制解除 |

解除时以 `force=1` 把设备端从 80/85/90 拉回 `thinking`(20)，并清空所有会话里残留的等待态，避免多窗口下 `sticky` 已清、`current` 却仍被别的会话等待态顶回来的失配。

### 7.6 调参与排错

| 现象 | 处理 |
| --- | --- |
| 想让「卡住」更早 / 更晚报红 | 调 `stalled_after_ms`；`0` 关闭 |
| 想看到「输出中」渐变 | 显式上报 `ai_status_state: "outputting"`；或把 `infer_outputting` 设为 `true`（注意深度思考会被近似成输出中，默认关闭） |
| 判断当前是否快卡住 | `GET /health` 看 `state.quiet_ms` / `state.stalled_after_ms` / `state.sticky` |
| 灯一直不解除 | IDE 既没发 `UserPromptSubmit` 也没发 `PostToolUse`；用 `python main.py clear` 手动释放 |
| 完成态时长 | 固定 10s，由 `done_hold_ms=10000` 与帧 `ttl=10000` 共同保证，改一处时另一处也要同步 |

## 八、设备发现顺序

1. 串口：枚举 `VID_303A:1001` / `VID_1A86:55D3` → `ping` 等 `pong` 且 `proto == ai-status/1`
2. 局域网：`cached_ip` → mDNS `esp32s3-ai.local` → ARP 按 MAC 前缀反查 → 并发扫 /24 的 `/api/hello` → AP 兜底 `192.168.4.1`
3. 都找不到：日志提示连接设备 AP；服务仍继续运行并定时重试

## 九、来源 ID（`src`）

- 每台电脑首次运行生成稳定 ID（主机名 + 随机后缀），写入 `client_id.json`。
- 所有状态帧、心跳、`clear`、`get`、`ping` 都带 `src`；`msg` 额外带 `[ID]` 前缀。
- 设备 v1.5.0 按 `src` 为每个来源独立维护状态，并在网页「来源与绑定」显示列表；可勾选只接受某几台。
- 查 ID：`python main.py identity`、`GET /identity`、`GET /health`。

## 十、日志与健康检查

- 控制台与 `ai_status.log` 同时输出，格式 `时间 [级别] 状态 -> xxx 原因 reply=...`。
- `GET /health` 是最有用的排错入口：`event_count` 为 0 说明 Hooks 没生效；`device.kind` 显示当前通道；`device.last_frame` 显示最后一帧（含 `src` 与 `msg`）；`state.waiting_for_human` 显示是否处于等待态，`state.quiet_ms` / `state.stalled_after_ms` 显示距离「判定卡住」还有多久。
- 服务不会把任何数据发到公网：事件总线只监听本机，设备接口仅可信局域网。
